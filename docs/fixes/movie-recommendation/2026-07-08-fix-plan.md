# Fix Plan: Enable explicit Neo4j transaction management and repositories configuration

## Root Cause

- **Confirmed hypothesis:** Hypothesis 1 and Spring configuration conflict. When using both Spring Data JPA and Spring Data Neo4j, Spring Boot enters strict repository mode but fails to properly initialize `Neo4jTemplate`'s `transactionTemplate` because both JPA and Neo4j compete for the default `transactionManager` bean name. This results in a `NullPointerException` when query executors inside `Neo4jTemplate` are created.
- **Evidence:** Running the test throws `NullPointerException` at `org.springframework.data.neo4j.core.Neo4jTemplate$DefaultExecutableQuery.<init>(Neo4jTemplate.java:1424)`.
- **Eliminated hypotheses:**
  - Hypothesis 2 (Incorrect GraphQL API path resolution) - The path resolved correctly via browser/routing, but backend throws errors on boot or query invocation due to NPE.
  - Hypothesis 3 (Authentication Principal issue) - The actual root cause was the NPE during SDN bootstrap.

## Fix Approach

- **Strategy:** Create a custom `Neo4jConfig` class that defines an explicit `neo4jTransactionManager` bean and registers Neo4j repositories via `@EnableNeo4jRepositories(transactionManagerRef = "neo4jTransactionManager")` to separate them cleanly from the default JPA transaction manager.
- **Files to modify:**
  - `web-film-backend/src/main/java/com/tamdao/web_film_backend/config/Neo4jConfig.java` (Created)
- **Risk assessment:** Low risk. This purely configurations separation of transactions between JPA and Neo4j.
- **Rollback plan:** Delete the `Neo4jConfig.java` class.

## Scope Guard

- **In scope:** Neo4j database transaction and repository mapping configurations.
- **Out of scope:** Modifying queries or graph synchronization logic unless verified broken after resolving NPE.
